# Harborline Pilot Readiness Protocol

## Purpose

This protocol prevents a polished demo from being mistaken for a validated product. It defines when the project should move from discovery to a narrow, client-specific pilot.

## A pilot is ready only when the workflow is defined

The first pilot is **not** “connect Harborline to everything.” It is one controlled workflow for one agreed user group, with a documented owner, data/context source, message boundary, automation posture, exception rule, and success measure.

| Pilot element | Minimum decision before pilot | Example for Reorder Reminder |
| --- | --- | --- |
| **Workflow** | One repeatable account moment. | No reorder in a defined cadence window. |
| **Audience** | An agreed small account segment. | One territory or selected retailer cohort. |
| **Signal / context source** | A permitted source or controlled sample data. | Approved order-history export or sandbox dataset. |
| **Owner** | Named responsible representative and escalation owner. | Territory Manager Renee Lewis equivalent. |
| **Message boundary** | Approved content and explicit exclusions. | Availability check; no price, terms, promotion, or allocation language. |
| **Automation posture** | Draft, rep-approved, or policy-approved. | Start with Draft or Rep-Approved. |
| **Exception rule** | Replies that must route to a person. | Price, credit, allocation, complaint, dispute, or special terms. |
| **Evidence record** | Fields retained for review. | Trigger, account, owner, message version, action state, reply, handoff. |
| **Success measure** | One behavior or outcome to compare. | Completion rate, time-to-follow-up, reply ownership, or rep-reported usefulness. |

## Readiness scorecard

Score each item **0 = absent**, **1 = partially defined**, or **2 = clear and confirmed**. The score guides a discussion; it does not override a client’s risk or policy requirements.

| Readiness test | 0 | 1 | 2 |
| --- | --- | --- | --- |
| **Real problem** | No specific pain described. | General interest only. | Repeated real examples of workflow breakdown. |
| **User acceptance** | Reps or buyers reject the posture. | Interest with major unresolved concerns. | Named users accept a defined draft/approval posture. |
| **Sponsor** | No accountable decision maker. | Interested contact only. | Sponsor agrees to a small workflow test. |
| **Data context** | No viable source. | Source exists but access is unclear. | Approved sandbox/sample or data path is identified. |
| **Control boundary** | Content or exception rules are unknown. | Partial rules identified. | Message, owner, approval, and exception rules are documented. |
| **Measurement** | No outcome is agreed. | General desire to “save time.” | A baseline and one success measure are defined. |
| **Total / 12** |  |  |  |

## Decision rule

| Score | Decision | What happens next |
| ---: | --- | --- |
| **10–12** | **Candidate pilot** | Draft a client-specific pilot brief and confirm data, ownership, and approvals. |
| **7–9** | **Promising; resolve gaps** | Run targeted follow-up discovery before committing build/integration work. |
| **0–6** | **Do not pilot yet** | Revise the product hypothesis, choose a different workflow, or stop pursuing this account. |

Regardless of total score, **do not proceed** if the client cannot name an accountable owner, will not permit a clear draft/approval boundary, or has unresolved policy objections to the proposed communication.

## The pilot brief to create after a positive decision

Write one page with the following headings: client and sponsor; workflow; account segment; signal/context source; assigned owner; message template and exclusions; approval mode; exception rule; evidence record; timeframe; success measure; excluded scope; and review cadence.

## What not to do yet

Do not promise live messaging, direct ERP/CRM access, automatic pricing/terms, policy-approved automation, or broad rollout solely because a buyer likes the demo. Those are implementation decisions after workflow evidence and client review.
